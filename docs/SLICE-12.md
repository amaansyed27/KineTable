# Slice 12 — Personal Workspace

Project v4 remains the editable document. Workbench undo/redo remains session-local. IndexedDB v5 adds `projectVersions` (immutable snapshots scoped by owner and project) and `projectConflicts` (both documents, base and cloud revision, detection time). Existing v4 stores and rows are retained by Dexie. A guest's versions are copied into an empty account only when its project is adopted. Sign-out and account switching query exact owner namespaces.

## Project memory and sync

`projects.revision` is a server-owned increasing integer. Migration `20260928171325_personal_workspace.sql` backfills revision 1 and one initial version per existing project, leaving IDs, owners and JSON documents unchanged. New browser writes use `checkpoint_project(id, document, reason, expected_revision)`. The PostgreSQL function checks `auth.uid()`, locks the head, compares revisions, updates or inserts the head and inserts a version in one transaction. It returns `{ status: "saved" | "conflict", project: head }`; a stale revision is an ordinary result and never an SQL serialization error. Direct browser INSERT/UPDATE/DELETE on `projects` and all browser writes to `project_versions` are revoked; owner-only RLS permits reads. Old clients' direct project writes fail closed.

Local changes save first. Project creation, circuit/wiring/logic edits, rename, AI Apply, manual checkpoints and restores record deterministic reasons. Repeated layout moves save the head immediately and settle into one local version after 900 ms; signed-in cloud sync checkpoints the latest document after 500 ms. Camera, selection, hover and simulation state never enter the project document or version history. Versions are not auto-pruned. Local and cloud history are validated through v1→v4 migration, electrical safety and logic checks before preview or restore. Restore creates a new head and version with the current project identity; older snapshots stay available.

A stale device never overwrites a newer revision. Sync stores a persistent local conflict with both documents, exposes it in the project header, Projects/Home and History, and pauses that project's cloud upload. History offers **Use this device** (new cloud revision), **Use cloud version** (preserve the device snapshot locally, then adopt cloud), and **Keep both** (cloud stays original; device copy becomes a new owned project). Resolution clears the record only after persistence succeeds. No structural merge is attempted. Another remote update during resolution asks the user to review again.

The initial checkpoint RPC raised `40001` for an expected stale revision. The request path treated that SQLSTATE as retryable, and the client also had an immediate `syncAgain` followup. During hosted QA, `PROJECT_CONFLICT` errors reached roughly 6,000/minute. The emergency `20260928192917_pause_slice12_checkpoint_loop.sql` migration made the RPC read-only while production was cleaned and the fix was tested. The final resume migration restored writes with the tagged result above; it passed local checks and was applied to production as `20260929000000` during the approved Slice 12 production verification. The client treats a conflict as terminal until explicit resolution, allows at most one scheduled followup for a new local edit, and cancels pending timers on account change. Network failures remain locally saved and retry only through a later user action, online event or new edit. This recovery is forward-only; neither applied migration is rewritten.

Fresh authenticated routes hydrate profile and then restore exact project heads and cloud history; `/projects/:id`, History, Projects and Explore do not require visiting another page first. Account sync combines profile, all locally dirty projects, inventory dirty rows, inventory sync status and persistent conflicts. Inventory still uses Slice 11's timestamp reconciliation; concurrent inventory edits are not given the project conflict guarantee.

## Explore

`/explore` has five curated, static ideas: Blink LED, Button controls LED, Motion alarm, Temperature display and BONK. Requirements reference canonical component IDs and fail at load if definitions, quantities or declared board compatibility are invalid. Matching counts explicit owned board and part quantities. The selected virtual board is a compatibility signal, never proof of ownership. Ranking is deterministic: ready, compatible, fewest missing, then name. Empty inventory shows supported ideas without claiming readiness. No model call, account or network is needed.

The detail shows the build intent, learning concept, supported boards, simulation claim, exact owned/missing quantities and a Start action. BONK reuses its validated deterministic starter. Other ideas create a real blank project with curated intent and board through the existing local-first creation path. My Parts quantities do not decrease. The workbench offers manual building and optional existing AI assistance afterward.

## Scope and limits

No collaborative editing, graph merge, community content, purchasing, Learn, code generation, flashing or hardware runtime was added. Project histories are currently fetched up to 100 cloud versions in the UI; older rows remain in the database and may need pagination if users accumulate more. Inventory remains last-write by timestamp. Cloud connectivity is optional for local project history and Explore.
